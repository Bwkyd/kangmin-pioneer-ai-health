# 问卷前科普修复候选验证与评审

## 问题与边界

作者反馈聊天只能机械进入问卷。真实 CLI 连续提问“什么是过敏性鼻炎？”、“为什么早上
起床会连续打喷嚏？”、“它和普通感冒有什么区别？”，均返回问卷第一题；同一个模型 Key
通过独立知识问答却能正常回答。原因是自由对话服务在问卷完成前只处理事实提取和规则
补问，普通科普没有接入生成链路，和现行意向中问卷前科普的要求不一致。

本次修复 CLI、HTTP 流式入口与原生小程序共用的服务；不修改临床规则、证型/分期标准、
数据库 schema 或身份权限。任务分支从远端 `main@7563140` 建立，主工作区另有任务前
未交付成果，均未混入本次分支。主工作区的既有故障记录编号不复用，本分支以评审编号 `050` 记录最终候选与交付证据。

## 历史根因复核

2026-08-18 的 `7eb9323` 中，小程序问助手已经调用 `agent exec`；后续 `2c50d3b`
只是把这一调用换为流式传输，没有改为科普入口。2026-08-23 的 `3d794b7` 确实恢复了
一般科普，但会话服务的生成入口仍位于 `execCompletedFollowUp`，即完成评估后；同版
Web 的 `DiscoverView.submitKnowledge` 则通过独立 `askKnowledge` 提问。两条路径
不能互相替代验收。本轮同 Key、不同命令的真实 CLI 对照再次证实入口差异。

因此已定位的是问卷前问答长期漏接、入口与会话阶段验收遗漏，不能把此前“能回答”
扩大解释为小程序新会话也能回答；目前没有证据表明是换 Key 导致原先完整能力退化。
此前微信登录配置缺失是另一层可用性故障，恢复配置后才显露此行为缺口。

PR #424 的首次 CI 则在 legacy 的生产依赖审计失败，尚未执行本次问答检查。锁定的旧版
Next、sharp、source-map-js 等命中当前漏洞库；升级作为作者授权的独立提交主题，保持
审计阈值。未逐条核对公告发布时间，不把“新增公告”当作已确认的具体时间归因。

## 修复

- 问卷前使用 Qwen 判断当前输入是普通问答，还是开始/回答评估；普通问答不调用事实
  提取、不自动开问卷、不生成个人调理方案。结构化选项继续走确定性解析和规则。
- 问卷前和判定后均以真实 role 传递最近六条历史，把本轮问题放在最后一条 user 消息；
  不把历史重新尾置在本轮 JSON 中，避免模型回答旧问题。
- 插问的正文可以解释科普，原待答节点保持不变；同一个 `visibleQuestions` 同时用于
  实时响应和持久化，刷新后不会突然消失或重新出现选项。
- “有口渴是什么原因？”不能被截成“有口渴”写入患者事实。旧解析器的完整明确症状
  陈述仍可解析，问题句交给问答链路。
- 急症优先于确定性答案解析和模型调用；混合“口渴：是，呼吸困难”也不写新事实，
  结束当前未完成评估、清空待答并拒绝沿旧会话续评。采用现有非 classified 的 completed
  终态，避免刷新后被误报为规则变更。
- 共用的检索和历史读取抽到无状态 helper，写库和 CAS 仍由会话服务负责。检索失败可
  一般科普，历史完整性错误不吞掉，模型失败明确提示重试。
