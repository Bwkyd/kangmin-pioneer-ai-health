# 管理后台缺陷修复可行性与发车门

- 状态：已完成
- 日期：2026-08-28
- 代码基线：`main@947e87a`；实验使用同一基线构建出的 `src/dist`
- 范围：Open Issue #390–#397 对应的 G1–G3 仓内修复线；#385–#388 只检查仓内准备度，不把外部验收伪装成通过

## 假设与变量

假设是：已有测试、隔离 SQLite、HTTP 入口和 Chromium 验收入口足以分别验证状态写入、审计缺口、登录限流和后台主流程；需要确认的架构变量是“内容写入与审计是否能通过现有 repository 外层包裹进同一事务”。小程序正式链路的 AppID、微信权限、合法 HTTPS 域名、真实设备和客户验收不在本实验内。

## 证据与验证

| 检查 | 结果 | 意义 |
| --- | --- | --- |
| `npm run build --silent` 与 core/content/record/shell smoke | 通过：2/2、2/2、3/3、6/6 | 基线可构建，基础业务入口没有先行回归 |
| 小程序源码回归检查 | 通过：4/4 | 仓内小程序检查点可运行，但不等于正式微信验收 |
| `node scripts/web-browser-e2e.mjs` | 通过 | 管理后台真实 Chromium 验收入口可启动并完成主路径 |
| #390 隔离 SQLite 复现 | 通过复现：已发布消息编辑后仍为 `published`，`published_at` 未清空 | 确认发布状态编辑缺陷真实存在 |
| #394 隔离 SQLite 复现 | 通过复现：新增消息后的审计动作只有 `content.message.publish` | 确认 create/update 审计缺口真实存在 |
| #395 隔离 HTTP 复现 | 通过复现：`POST /v1/admin/session` 连续两次错误密码均为 `401`，无 `Retry-After` | 确认实际登录入口未接入限流 |
| #394 事务边界探针 | 通过复现：现有数据库事务嵌套报 `cannot start a transaction within a transaction`，失败后表计数为 0 | 不能只在 service 外层套现有 repository；需共享事务入口 |

实验耗时约数分钟，未改动生产环境、truth、患者数据或外部微信配置。已有的浏览器级缺陷证据和源码路径复核继续由 `docs/reviews/047_admin-backend-defect-review.md` 承担；本实验不把一次未完成的自定义浏览器探针当作通过证据。

## 结论与发车判断

结论：G1–G3 具备仓内发车条件，且不需要新增产品或医学决策。执行顺序保持 G1 → G2 → G3；G2 的第一检查点是先建立内容写入与审计共享事务的最小实现，再扩展文章、视频、站内消息和 SQLite/PostgreSQL 测试。若事务边界无法同时满足两种数据库，停在该检查点，不降级为“内容成功、审计失败”。

推断：按当前代码边界，#390–#397 可以通过实现、窄测、浏览器路径和完整门禁逐组收敛；这不是客户验收、临床批准、生产就绪或 GitHub Issue 关闭承诺。

外部发车条件仍未满足：#385 需要正式 AppID/权限/合法 HTTPS 域名/受控网络和身份；#386–#388 还需要真实服务联调、正式内容、双平台真机和客户确认。仓内可以先补齐配置失败关闭、联调契约和测试，但不凭本实验关闭这些 Issue。

## 发车后的停止门

1. 每组先跑针对性窄测；失败先修复，不把已知失败加入白名单。
2. #394 必须证明内容和审计同一事务全成全败，并覆盖 SQLite 与 PostgreSQL 适配器。
3. #395 必须证明账号与可信客户端 IP 的独立限流，默认不信任任意 `X-Forwarded-For`。
4. #391/#392 不在浏览器保存原始文件；恢复文本/元数据时必须有明确确认和重新选文件路径。
5. 组内修复后再跑 `npm run check`、真实 Chromium 路径和 `git diff --check`；外部资源未配置的跳过项单独报告。
