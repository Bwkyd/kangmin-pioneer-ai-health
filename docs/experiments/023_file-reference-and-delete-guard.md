## 问题与停止线

本实验只裁决两个分叉：引用去向由浏览器用已加载业务列表推断，还是由服务端按数据库关系
权威返回；删除保护只阻止当前患者可见引用，还是阻止所有仍存在的业务引用。

停止线：文章/视频的文件、封面、正文附件和 AI 知识源文件均能显示名称、状态与用途；草稿、
下架、未启用知识仍属于“正在使用”，不能直接删除；无引用文件可删除且不影响三类上传、发布、
启用或患者访问。实验不新增迁移，不扩展标签、审批、批量迁移或独立素材工作流。

## 假设与变量

- H1：仓储批量返回引用关系，能避免前端状态快照漏掉正文附件或知识源，并保持 SQLite/PG 同构。
- H2：事务内统计所有状态引用并拒绝删除，比自动清空草稿/下架/未启用引用更符合“仍被使用
  不能删除”，也不会改变已发布内容和已启用知识的既有保护。
- H3：二级“文件管理”只从文章、视频和 AI 知识页的次要入口进入，并按图片、视频、知识文件
  与附件分组，可满足清理与引用检查而不恢复一级素材库心智。
- 对照方案：浏览器用文章、视频和知识列表拼接引用。该方案无法可靠识别正文附件，也可能把
  未加载或并发变化的关系显示为无引用，因此不作为首选。

## 基线证据

- 内容/文件窄测 18 项中 17 通过、1 项因本机未配置 PostgreSQL 跳过、0 失败。
- 现有真实浏览器 E2E 全链路 PASS；一级侧栏已无素材库，三类任务内上传已存在。
- 现有删除事务只统计已发布内容和已启用知识，并会自动断开其他状态引用；列表不返回具体去向。

## 预期成本与限制

- 增加一个跨素材的批量引用读模型，更新 SQLite/PG 查询与契约测试；不改表结构。
- 删除守卫继续与写入同事务，避免检查后新引用竞态；对象删除仍只在数据库删除成功后执行。
- 正文附件沿用当前 `/v1/media/<id>` 引用格式；本实验不引入正文 AST 或文件版本关系。

## 结论与证据

- H1 通过：SQLite 与 PostgreSQL 均以一次批量查询返回文章/视频文件、封面、正文附件和
  AI 知识源文件的名称、状态与用途；服务层按文件 ID 组装，避免逐文件查询。
- H2 通过：删除守卫统计所有状态的内容与知识引用，不再静默清空草稿、下架内容或停用知识；
  SQLite 服务测试覆盖“下架后仍拒绝 → 业务显式移除 → 删除成功”，PG 契约覆盖四种引用角色。
- H3 通过：文章、视频和 AI 知识页提供次要“文件管理”入口，一级导航仍无该入口；文件页无
  上传表单，并按图片、视频、知识文件与附件筛选。
- `cd src && npm run check` 通过类型、架构、小程序、全量测试和真实浏览器 E2E；浏览器在
  390×844 与 1440×1000 路径核验三类引用、下架/启用状态、禁删按钮及未使用文件真实删除。

本机没有 PostgreSQL 运行时，PG 契约按项目约定由 GitHub CI 的 PostgreSQL 16 服务强制执行。
正文附件继续依赖 `/v1/media/<id>` 格式；不把本实验扩大为正文 AST、文件版本或批量迁移。
