# 客户决策：结构拆分采用机会型触发

- 状态：作者已确认并实施
- 创建日期：2026-08-27
- 归档日期：2026-08-28
- 决策基线：`origin/main@783cb74`

## 背景与决策点

当时四组快速冒烟入口已建立，存量长文件仍可运行；模型端口测试拆分还出现“行数下降但导航成本上升”的负向证据。没有真实功能变更作为触发点时，继续强拆会新增入口、fixture 和依赖关系，可能让“降低复杂度”反而增加复杂度。

需要选择：等待真实变化再拆；继续实验低风险测试文件；或立即拆小程序助手与壳层。后两项分别存在重复实验成本和患者流程风险。

## 最终结论

作者在 2026-08-27 对话中回复“好的，根据你推荐的来”，确认采用“等待真实变化再拆”：

- 不以超 600 行占比或 3% 数字单独启动重构；长而内聚可以保留。
- 只有功能、缺陷或反复修改触及明确变化轴时，才在同一小交付内先做冒烟和有界实验，再按能力边界决定是否拆分。
- 每轮不超过四个实体，设置正反检验与停止线；不为目录整齐制造转发壳、重复 fixture 或近似重写。

该选择保持当前成本和运行风险最低，同时允许真实变化提供拆分边界和收益证据。

机会型长文件 Issue 后来统一以 `not planned` 关闭，不再冒充活动待办。随后管理后台出现明确的结构触发点，另开 #364–#369，以真实 Chromium、完整回归、导航成本和复杂度双线验证完成最小分形拆分；`AdminApp.tsx` 从 1348 行收敛到 212 行后停止继续拆 Login/Overview、消息和文件。最终实现已通过 PR #370–#375 合并并部署，说明本决策约束的是“无触发强拆”，不是禁止有证据的小步结构治理。
