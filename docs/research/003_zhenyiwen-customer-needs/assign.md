【角色】

客户原话和 truth 是“要比的”；分析基线代码与实验是“零件”；既有框架调研只作架构参考。

【逐条核查】

1. 客户是否明确要求保留规则判定、改为动态解释并在方案后持续追问？
2. 报价是否覆盖“规则引擎 + RAG + 大模型自然语言解释”，哪些细节仍未获得 truth 授权？
3. 分析基线代码是否已有规则裁决、模型调用、输出校验、知识问答和会话持久化？
4. 分析基线代码离客户可感知的动态生成与方案后追问还缺哪几根连接？
5. 已有千问实验是否足以决定下一步，最不利证据是什么？

【分析时预判——请推翻我】

不需要换 Agent 框架或重做规则；需要先让客户确认验收边界，再把现有规则、模型、校验、
知识和会话能力接成一个最小闭环。

【证据格式】

只使用 `文件:行号 + 事实 + 判断`；没有就明确说没有。客户 raw 只追溯意图，不反向覆盖 truth。

【字数上限】

汇总结论 800 字以内。

【必须给判断】

首选：复用现有实现并补齐闭环。备选：保留固定模板，只增加独立知识问答入口。必须同时
报告三个最大风险，不得只报首选。

## 冒烟结果

- 核查项能由原始聊天、报价、分析基线代码和实验逐条回答，没有停在“看情况”。
- 首选明确；备选虽然风险较低，但无法解决客户点名的“千问没起作用、方案后不能追问”。
- 外部框架不是当前信息缺口，因此停止扩展取材。

## 核查回收（分析基线 `main@0a2c312`）

   让千问动态解释并在问卷后持续追问；判断：需求主干清楚。

   解释、视频和知识库维护；没有轻重症规则、模型生成视频或无边界自由诊疗授权。
3. `main@0a2c312:src/modules/agent/conversation-service.ts:342-390` 与
   `main@0a2c312:src/modules/agent/output-validation.ts:223-277`：已有规则、会话、模型钩子和

4. 同一基线未找到完成会话继续输入、当次方案白名单追问和来源引用路径；判断：需补方案
   载荷、千问端口、追问分支、输出校验和 Web 入口，不需换框架。
5. `docs/experiments/001_zhenyiwen-constrained-dialogue.md:13-16,41-58`：6 回合原型支持方向，
   但曾自创数值/操作，检索召回有噪声；判断：足以决定“小闭环”，不足以证明生产质量。

**首选**：改造现有实现，接成端到端最小闭环。**备选**：固定方案不变，只开放独立知识

越界必须由代码降级，不能只靠 Prompt。
