# 抗敏先锋对抗性审查

## 目标

以精确候选 SHA 为对象，分别从不同视角寻找重复实现、并发与边界缺陷、旧功能回归和临床/内容发布越界。审查过程只读，不修改代码、不提交、不部署、不关闭 Issue；结论必须有文件、行号、测试或运行证据。

## 审查前置

1. 记录仓库、分支、候选 SHA、关联 Issue/PR 和工作树状态；确认审查的 SHA 未漂移。
2. 阅读关联 Issue 的单一需求、非范围、验收标准和待确认项，再阅读实现的完整调用链；不要用聊天摘要替代 Issue 正文。
3. 检查数据库迁移、API 鉴权、前端入口、公开查询、媒体直链、规则测试和已有 E2E；只看必要范围。
4. 将“本地测试、CI、后台可达、浏览器 UAT、客户/临床确认”分别记账；一个绿灯不能替代另一个门禁。

## 四个独立视角

每个视角单独输出，不读取其他视角的结论；可由四个隔离 worktree 或四个独立审查任务承担。

### 1. 重复与冗余

- 检查多个 Issue 是否把同一需求重复实现，尤其是历史总览与已拆分子 Issue。
- 检查入口、字段、状态枚举、数据库列、媒体上传逻辑和校验逻辑是否重复且含义不一致。
- 检查“姜刮”和“刮痧”、文章和视频、草稿和待审核、空值和 `unknown` 是否被错误合并。
- 输出最小删除/合并建议；不能因为看起来相似就删除客户要求的独立能力。

### 2. 并发与边界

- 检查重复提交、幂等键、快速切换页面、过期响应、下架与播放并发、上传失败、刷新和返回路径。
- 检查历史记录是否追加而不是覆盖，用户数据是否按身份隔离，缺失值是否被当成已知值。
- 检查发布状态在列表、详情、搜索、通知和媒体直链上的一致性；发布前的媒体必须不能公开访问。
- 检查空状态、错误状态、超大/不支持文件、无数据库或无 R2 绑定、网络失败和移动端长列表。

### 3. 旧功能回归

- 检查首页、对话、评估/过敏日历、健康档案、学一学、后台登录和既有规则 API 的原路径。
- 检查新增导航是否把健康档案误指向过敏日历，或让“换季为何反复”重新跳回错误入口。
- 检查固定规则引擎仍先于模型；模型只能解释或检索批准内容，不能自行生成诊断、证型、方案、药物或临床禁忌。
- 检查既有免责声明、高危信号就医提示、未审核内容不可见和 `unknown != no` 没有被 UI 文案或 fallback 破坏。

### 4. 临床安全与交付门禁

- 临床候选内容（#88–#99）没有临床负责人书面批准时，必须保持候选/待审核，不能进入 AI 提示词、正式规则或用户端。
- “鼻三线姜刮”必须与“刮痧”类型分开；艾灸、电吹风、耳穴压豆不得复用未经批准的刮痧安全规则。
- 任何刮痧推荐先处理急性发热、皮肤/出血风险和其他已批准的拦截；不确定答案不得按“否”处理。
- 科普内容只能在 `published` 且媒体有效时公开；下架必须同时阻断列表、详情和媒体访问。
- 检查是否把定向测试绿灯、旧 SHA 审查、超时或“没有发现问题”误写成完整 PASS。

## 输出格式

按以下格式输出，问题从 P0 到 P2 排序：

```text
审查对象：<repo> <branch> <sha>
关联范围：<issues/pr>

P0
- [file:line] 问题；证据；用户/安全影响；最小修复；验证命令

P1
- ...

P2
- ...

未发现问题但已检查：<调用链/测试/运行路径>
最终结论：PASS | FAIL | BLOCKED
结论条件：P0=0 且 P1=0；P2 必须明确接受、延期或转 Issue；BLOCKED 必须写精确阻塞和恢复条件
```

## 修复后的复审

1. 修复后重新冻结 SHA，只审查新 SHA；不得复用旧 SHA 的 PASS。
2. 先做修复差异审查，再重新跑受影响的全链路测试；每个 P0/P1 必须有对应证据。
3. Kimi 和 DeepSeek 独立审查同一精确 SHA，不互相读取结论；缺少最终 verdict、审查超时或审查对象漂移均为 BLOCKED，不是 PASS。
4. 只有全部 P0/P1 为零、必要 P2 有明确处理、构建/单元/API E2E/浏览器 UAT/后台 UAT/客户或临床确认分别通过，才可建议合并、部署或逐条关闭 Issue。

## 禁止事项

- 不把客户未确认的临床资料写成正式规则。
- 不把演示态内存状态说成真实持久化，不把 API 可达说成浏览器或生产验收通过。
- 不自行推送 `main`、合并 PR、部署、关闭 Issue、删除 worktree 或修改秘密。
