# kangmin 项目文档导航

`docs/` 保存需要长期追溯的计划、评审、研究、客户决策和已采用变更。
[`state/board.md`](../state/board.md) 按轮倒序记录实际变化、验证、遗留和待办；详细
计划、评审过程和决策内容留在对应文档，board 只保留接续所需摘要和链接。文档中的
日期、代码行号、完成度和测试数字只适用于其声明的基线。

## 阅读入口

| 需求 | 入口 |
| --- | --- |
| 当前系统能力与运行方式 | [`src/README.md`](../src/README.md) |
| 设计、交付计划和已完成修复方案 | [`plan/`](plan/) |
| 完成度、安全、代码和交付评审 | [`reviews/`](reviews/) |
| 专题调研 | [`research/`](research/) |
| 客户待决策事项 | [`product/`](product/) |
| 已采用的重要变更 | [`changes/`](changes/) |
| 客户来源与确认版本 | [`../vault/raw/`](../vault/raw/) 与 [`../vault/truth/`](../vault/truth/)（私密、本地例外） |

## 分类规则

- `plan/` 回答“准备或曾经准备怎样实现”，包括目标设计、交付计划和修复方案；
- `reviews/` 回答“在指定基线发现了什么”，包括复核结论和保留的原始输出；
- `research/` 回答“为了决策研究了什么”，不得把调研推断写成当前事实；
- `product/` 只保存需要客户选择的决策单和模板，普通产品计划放 `plan/`；
- `changes/` 保存已经采用、需要长期追溯的架构、运维和修复记录；
- 客户来源统一存放在 `vault/raw/`，客户确认采用版本统一存放在 `vault/truth/`；
  两者均不得提交、公开或复制到产品公共资源。

## 编号

- `plan/`、`reviews/`、`research/` 共用三位全局流水号，格式为
  `NNN_kebab-case.md`；已使用编号不删除、不复用；
- `001`–`003` 已由 `changes/arch/` 的历史变更记录占用；本次整理从 `004` 继续；
- 客户决策是例外，按 `YYYY-MM-DD-<topic>-decision.md` 命名，便于按沟通日期检索；
- 各目录 `README.md` 和 `TEMPLATE_*.md` 不占流水号。

## 文档最低信息

新增长期文档至少写明：状态、日期、事实或代码基线、目标与非目标、证据来源、
验证方式和已知限制。历史文件原则上不改写结论；需要纠正时新增复核文档并建立
关联。

## 隐私与事实边界

- 当前代码、测试、CLI `--help` 和真实运行结果决定系统实际行为；
- `vault/raw/` 保存来源，`vault/truth/` 中客户确认版本是当前开发和验收依据；
- 私密资料不得进入 Web 公共资源、Issue、PR、日志、截图或模型输出；
- 引用历史行号时同时写明基线；基线变化后重新定位，不按旧行号直接修改代码。
