# arch/002 服务端规则驱动动态补问

## 背景与动机

首个 MVP 已能通过服务端固定规则完成安全、适用资格、严重度和证型判断，但用户端仍固定询问全部 15 项。即使已经命中高危条件、确认未确诊，或现有答案足以得到唯一结果，页面仍会继续询问无关问题。

本次把会话导航交给现有 `/api/v1/agent/evaluate` 返回的状态和 `nextQuestions`，减少无效问题，同时不在浏览器中复制医学判断。

## 技术选型

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 前端按固定数组逐题前进 | 不采用 | 无法提前阻断，也不能利用规则已经确定的结果 |
| 前端复制安全、严重度和证型规则 | 不采用 | 会形成第二套临床逻辑，容易与服务端漂移 |
| 每次确认后由服务端评估并返回下一题 | 采用 | 保持服务端为唯一规则权威，可测试且能安全短路 |

## 数据模型

- 未回答字段在提交给规则引擎时统一填充为 `unknown`，绝不当作 `no`。
- 浏览器状态仍区分“未回答”和“用户明确选择不确定”：
  - 未回答：`answers[field] === undefined`，允许作为下一题；
  - 明确不确定：`answers[field] === "unknown"`，不得循环追问。
- 不保存健康数据，不改变首个 MVP 的无状态 API 边界。

## 架构设计

1. 会话从高危筛查开始；每次回答后调用服务端 `evaluate`。
2. `need_more_information` 只从服务端 `nextQuestions` 选择尚未回答的字段。
3. 安全筛查结束后，如果确诊前提尚未回答，则补问确诊状态；用户明确回答“否”或“不确定”后转诊结束。
4. `blocked` 立即展示安全拦截，不进入自由描述、严重度或证型。
5. 当严重度或证型已经确定时，服务端可跳过不影响结论的剩余字段，进入提交前复核。
6. 用户返回修改时清除旧评估和旧解释，再走同一服务端导航。
7. 浏览器不可用时必须单独标记真实点击旅程为 `BLOCKED`，不能以 HTTP E2E 替代。
