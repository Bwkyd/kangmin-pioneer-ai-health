# 003 最小客户试用版定义、验收与下一阶段开发计划

> 日期：2026-08-05  
> 代码基线：`main` / `cc79ac5`  
> 目标：给客户一个受控链接，让客户独立体验核心流程并提出修改意见；不是正式生产上线、医疗验收或小程序最终交付。  
> 原则：先让客户验证方向，再根据反馈继续开发，避免提前堆积可能返工的功能。

## 一、最小客户试用版的定义

最小客户试用版不是“功能最少的版本”，也不是“开发人员在自己电脑上能演示的版本”。它的定义是：

> 客户拿到链接后，不需要开发人员陪着操作，就能顺利体验核心流程、理解产品当前能力和边界，并给出有效反馈；同时不会遇到明显错误、数据串用、安全风险或能力误导。

它必须同时满足五个条件：

1. **可进入**：客户有稳定链接，可以直接打开并完成必要授权；
2. **可体验**：至少一条核心业务闭环可以从开始走到结果；
3. **不误导**：已完成、演示中和未开放的能力区分清楚；
4. **安全可控**：不同体验者数据隔离，高危健康输入安全阻断；
5. **能收反馈**：客户体验后能够对流程、内容和优先级作出判断。

如果只能由开发人员操作，属于内部演示版；如果客户能自行体验并反馈，才是客户试用版；如果要长期保存真实健康数据、正式给出个性化方案并承担服务承诺，则属于正式生产版。

## 二、三个版本层级的边界

| 层级 | 目的 | 允许的限制 | 不能出现的问题 |
| --- | --- | --- | --- |
| 内部演示版 | 开发自测、团队展示 | 本地地址、预置账号、人工造数 | 不要求客户可独立使用 |
| 最小客户试用版 | 让客户确认需求和方向 | 部分功能暂未开放、演示内容、短期数据 | 核心流程报错、数据串用、死按钮、虚假能力声明 |
| 正式生产版 | 面向真实用户长期服务 | 只能保留已披露的产品限制 | 不完整认证、未经审核的医疗输出、缺少生产运维保障 |

本轮目标只做到第二层，不提前承担第三层的全部工作。

## 三、本项目最小试用范围

客户至少可以独立体验四条主线：

| 主线 | 最小可体验结果 |
| --- | --- |
| 首页与导航 | 看懂产品提供什么，并能进入主要模块 |
| 问助手 | 输入问题并完成至少两轮对话；高危内容得到安全提示 |
| 健康记录 | 新增症状，看到 TNSS、日历和趋势；刷新后记录仍存在 |
| 科普内容 | 打开至少两篇文章和一个视频，确认内容展示方式 |

仓库 `legacy/app/admin/` 中确实存在旧版可视化后台，包含登录、文章、视频、知识、素材和审核页面，但它属于 `legacy/` 旧系统，使用旧 API 和数据模型，当前 `https://49.232.26.48` 部署的是新 `src/` 服务。旧页面不能直接视为当前线上管理后台，也不应为了赶进度把两套业务状态重新混用。

#### 旧后台复用决策

采用“复用旧页面外观和交互，改接新架构服务”的方案，不重新设计一套后台：

- 可直接复用：`legacy/app/admin/admin.css` 的视觉样式，以及 `legacy/app/admin/page.tsx` 的侧栏、工作台、内容表格、编辑表单、素材库、登录页和状态提示结构；
- 需要适配后复用：去掉 Next `Link` 和 `@/` 旧模块依赖，按当前 Vite/React 目录拆到 `src/web/src/admin/`；只保留报价范围内的文章、视频、素材和知识模块；
- 不可搬用：`legacy/app/api/admin/**`、`legacy/lib/admin/auth.ts`、`legacy/lib/admin/store.ts` 及旧迁移。它们绑定 Cloudflare D1、R2、Vectorize 和旧管理员 Cookie，不能与当前 Node + SQLite 服务并行维护；
- 新接入点：页面统一调用当前 `/v1/admin/commands`；登录应通过当前管理账号体系，并优先由服务端写入 HttpOnly 管理会话 Cookie，不能把管理员令牌长期放在浏览器 `localStorage`；
- 上传需重接：旧页面直接提交 `FormData`，新服务应复用 `upload-init → 上传 → upload-confirm` 远程上传协议；知识资料上传后走 `agent knowledge add-from-media`；
- 必须验证：后台发布文章/视频后患者端可见，下架后不可见；知识资料能够上传、索引、启停和检索测试；管理员与患者会话严格隔离。

预计旧页面视觉层可复用约 70%，但连同认证、命令适配、浏览器上传和端到端测试计算，整体开发量可节省约 40%～50%。这比重做后台更合适，也比直接部署 `legacy/` 更安全。

## 七、如何判断和验收

### 7.1 验收总原则

只有同时满足以下条件才算通过：

- 所有一票否决项为零；
- 客户核心路径验收项 100% 通过；
- 没有未处理的 P0，且没有阻断核心路径的 P1；
- 非核心限制已经明确标注，不会被误认为故障；
- 使用客户最终收到的链接完成两遍验收；
- 至少使用两个独立浏览器验证数据隔离；
- CI `quality` 全绿。

### 7.2 一票否决项

出现以下任意一项，不允许把链接发给客户：

- 链接打不开、频繁报错或首次进入就是技术错误；
- 需要客户执行命令、修改数据库或联系开发人员才能继续；
- 新增、修改或保存核心记录失败；
- 不同体验者能够看到或覆盖彼此的数据；
- 核心按钮点击没有反应；
- 页面宣称能辨证或推荐方案，但答案实际上没有进入对应链路；
- 高危症状仍然返回普通居家调理建议；
- 未经审核的内容被包装成正式诊断或治疗建议；
- 客户没有访问权限，或管理端意外对客户开放；
- 页面或日志泄露令牌、健康正文、密码或内部文件路径。

### 7.3 最终链接验收清单

#### A. 访问与首屏

- [ ] 客户链接可以直接打开；
- [ ] 指定客户账号或邮箱拥有访问权限；
- [ ] iPhone 宽度和普通桌面浏览器均可使用；
- [ ] 首屏无空白、错位、404 或技术错误；
- [ ] 页面明确标注“客户反馈体验版”；
- [ ] 页面提示不要录入真实患者隐私信息。

#### B. 新访客、授权与隔离

- [ ] 新访客可以在页面完成体验授权；
- [ ] 不需要执行 CLI；
- [ ] 授权后可以读取和保存记录；
- [ ] 两个无痕窗口获得不同体验身份；
- [ ] 两个窗口分别保存记录后互相不可见；
- [ ] 会话过期后有清楚、可恢复的提示。

#### C. 健康记录闭环

- [ ] 新增一条症状记录成功；
- [ ] TNSS 计算正确；
- [ ] 日历能显示刚保存的记录；

## 十、客户反馈之后的开发方向

患者端反馈回来后，先整理并确认需求，再决定非报价扩展项，不应现在提前全部开工。但管理后台已经写入报价表，不属于可无限后置的扩展需求。建议按以下顺序推进：

1. 用一轮小改动隐藏或标注患者端 5 个无行为入口，并完成线上手机验收；
2. 开发新架构的最小管理后台 Web：管理员登录，以及文章、视频、素材、知识资料的列表和必要操作；
3. 将后台 Web 接到现有 `/v1/admin/commands`、同一数据库和素材目录，部署后验证“后台发布 → 患者端可见 → 后台下架 → 患者端不可见”；
4. 根据客户反馈调整首页、问诊题目、记录维度和方案展示；
5. 完成固定临床规则冻结，接通受控 RAG 和模型解释；

管理后台建议拆成 2 轮开发和 1 轮联调部署：第一轮完成登录、页面骨架和只读列表；第二轮完成文章、视频、素材与知识的新增/编辑/上下架或启停；第三轮完成端到端联调、线上权限和部署验收。先严格覆盖报价表，不在这一阶段额外开发用户管理、复杂统计、模型参数中心或临床方案后台。

## 十一、本轮不做的内容

- 微信小程序真机套壳和上架；
- 正式手机号或微信登录；
- 超出报价表的后台能力，例如复杂用户运营、统计报表和多级审批中心；
- 完整 RAG 和知识库问答；
- 真实花粉、天气或环境数据供应商；
- 提醒通知、数据导出和账号删除；
- 所有证型和康复方案一次性录完；

固定规则的临床冻结、个性化证型和正式康复方案输出仍然是正式产品硬门槛，但不是本次页面和流程确认链接的硬门槛。体验版必须明确不会输出正式诊断或治疗建议。
