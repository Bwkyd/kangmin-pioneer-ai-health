## 目标与边界

用一条可重复命令验证报价范围内的四条业务链，发现问题后在同一轮修复并复测。
本轮不改 `vault/truth/`、医学规则和正式患者数据，不恢复已退役的患者 Web，也不把技术
预验收表述为客户验收、微信真机验收、医学批准或生产就绪。

## 四个验收实体

| 实体 | 真实入口 | 正向证据 | 失败关闭证据 |
| --- | --- | --- | --- |
| 内容运营 | 管理 CLI、HTTP、浏览器后台 | 登录、创建、发布、患者只见已发布内容 | 未发布内容与媒体不可见，非法请求被拒绝 |
| AI 知识 | 管理 CLI、患者 Agent | 上传、索引、测试、启用后可检索 | 未启用不参与回答，模型失败不泄露检索切片 |
| 患者核心 | 小程序壳、患者 Agent、HTTP | 完成测评、确定性分期/证型/方案并继续追问 | 高危、药量、未知状态和候选规则安全阻断 |
| 持续管理与交付 | 小程序壳、HTTP、SQLite | 授权后保存症状并回显概览、日历、趋势 | 未授权、跨患者、旧版本和非法输入被拒绝 |

实体总数为 4，不再拆子任务。测试使用隔离 SQLite；PostgreSQL、S3、OCI 留给 PR CI。
线上只允许无身份、无患者数据的只读探活。

## 执行顺序

1. 固化 `npm run test:acceptance`，一次构建后严格命中四组指定测试，并运行真实浏览器。
2. 用脚本内置的零命中与多命中反例自检，确认错误选择器会失败，防止“没跑也算通过”。
3. 运行四组正反路径；有 P0–P2 就补最小测试或修复，再从窄测逐级回归。
4. 运行 `src`、`legacy`、仓库结构门禁；由 PR CI 验证外部适配器与镜像。
5. 执行 sequential-thinking 元反思和 `$km-review` 三视角评审，P0–P2 清零后合并。

## 验收标准

- `npm run test:acceptance` 一条命令通过，且每组至少命中一条真实进程/HTTP/页面 E2E；
- 四组均同时有关键正向路径和至少一条 fail-closed 路径；
- 管理后台桌面与 `390×844` 浏览器路径通过，小程序结构与页面链路通过；
- `cd src && npm run check`、`cd legacy && npm run check`、仓库结构门禁通过；
- PR 的质量、PostgreSQL、S3、OCI 与镜像任务通过；
- 评审 P0、P1、P2 为 0，测试证据和外部限制写回 board 与 Issue。

微信开发者工具真机预览、客户业务验收和医学结论仍需作者或客户在真实环境拍板；自动化
