## 二、产量与存量

低频的时候，**一次破例占比极大**；旧资产质量不高时，除了修和删，
第三条路是**用新产出把它冲淡**。

**两个前提必须一起写，否则这条会变成「不用管旧账」**：

| | 填 |
|---|---|
| 新产出按什么新标准做 | 每条优化必须按真实变化轴拆分，不改外部行为、不降测试覆盖、不制造空转发层；医学和权限高风险路径继续 fail-closed |
| 存量什么时候迁移、迁哪些 | 先 #304 护栏与 #312 测试，再 #305/#306 Web 壳，然后 #308/#309 服务，最后 #307/#310/#311 数据库与双后端仓储；每完成一个可独立验收的切片再复诊 |

**占比下降不等于旧问题消失**——绝对债务和维护面反而更大。
**把分母做大本身不是治理结果，它只是给你争取到时间。**

# 减复杂度

> 只长不压：第一版挺满意，第十版没人 hold 得住。

**不是把东西删光，是让一次变更需要同时理解的东西重新变少。** 三件武器，每件都带反噬。

## 三、约束进四组

> 「这个软件再怎么复杂——一百多个功能——我也要把它约束在四组以内。
> 一组辅助，一组最核心，其他最多一到两组次要的。」

| 组 | 叫什么 | 装哪些东西 | 为什么是一组 |
|---|---|---|---|
| **核心**（必须有且只有一组） | 安全调理 | 问卷引导、truth 规则判定、通俗调理建议与判定后追问 | 它是项目的真难题，同一条患者任务链不能拆散 |
| 次要一 | 可信内容 | 文章、视频、AI 知识资料的运营维护、患者查看和受控检索 | 围绕「资料如何被维护并安全消费」同一变化轴 |
| 次要二（可省） | 持续管理 | 症状量表、按日保存、日历与趋势回看 | 围绕「患者的变化如何持续留痕」同一变化轴 |
| **辅助**（登录、帮助、配置一类） | 运行与治理 | 身份、权限、环境、部署、帮助、运营工作台及项目规约 | 它们支撑三个业务闭环，但不自己生成患者价值 |

**装不进四组的，写在这里**：

> （装不下说明还缺一层抽象，或者其中有些根本不该留。**别硬塞。**）

`<顶层>` 的 18 个目录主要是项目协议的六组物理分区，不是 18 个产品能力；
不应为凑四组重排根目录。真正需要压的是 `src/` 内的能力边界和长文件尾部。

**反噬提醒**：为了凑满四组，**把一个天然连续的流程拆到四处**——
以后改一次流程要在四个地方来回追踪。**宁可三组，不要硬凑四组。**

## 四、以 CLI 为中心

> 「先开发壳、没有先开发 CLI——这样的复杂度就非常容易失控。」

| | 现状 | 该是什么 |
|---|---|---|
| 核心能力住在哪 | `src/app`、`src/modules`、`src/kernel` 和仓储适配器；CLI/HTTP 已共用应用层 | **CLI / 库的核心层** |
| 界面（网页、桌面）是什么 | Web 与小程序主体是壳，但 `App.tsx` / `AdminApp.tsx` 的长度表明壳层仍吸收了过多页面编排 | **薄包装** |
| 自动化怎么调它 | CLI、HTTP、测试通过同一 application/module 调用；浏览器测试补真实交互 | 调同一个核心，不另起一套 |

**一处必须诚实的修正**：实测五个仓最宽的目录几乎都在网页端那侧，
但**网页框架的路由目录天然就是横向展开的，不必然是失控**。
所以准确的说法是：**壳那一侧天然没有收敛压力**；
**先做 CLI 的价值不在于壳不宽，在于宽的那部分不是能力所在。**

**反噬提醒**：把图形界面和库接口**硬塞进命令模型**，
内部逻辑会开始围绕参数解析组织，**领域能力反而难复用**。

## 五、最小分形结构

> 「森林无非是拆成一百万棵树，一棵树无非是再拆成树根、种子、树叶。
> 明白它的最小分形结构，再庞大也容易理解。」

**你这个系统的最小分形单元是什么？**（一个能力最少由哪几样构成）

>

`cog.md` 已给出最小分形：**一个工作单元**。它由一次患者或运营输入、
对应 truth/规则、受控处理、可回读交付物和一条可执行验收组成；小能力直接放平，
只有出现独立变化轴时才拆层。

**反噬提醒**：每个小目录都复制完整的四层壳，
**只有两个文件的能力也生出四层**，跳转次数与样板代码暴涨。
**分形是给大的用的，小的直接放平。**

**要拆的时候，按分组拆，不按行数拆**：不是把七千行切成七个一千行，
**是照着产品本来的分组切**。一个真实对照：两个仓的主文件都涨到约 6730 行，
一个当版按「产品三类命令」拆了，最长文件降到 1702 行，**而中位数只从 136 变到 138
——没有制造出一堆中等文件**；另一个没拆，下一版最大的换成了另一个文件，继续大。
这只支持「按能力/变化轴拆」，**不足以证明产品分组优于按领域、生命周期、
权限、部署单元拆**。别说死。两个 6730 是巧合不是控制实验，只作现象对照。
