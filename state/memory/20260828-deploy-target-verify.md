# 部署目标与运行路径先核实

部署前不能凭主机名、私钥文件名、旧记录或习惯目录推断目标。先从现行部署记录反查主机、用户和
密钥指纹，再通过只读检查交叉确认：

1. 使用 `systemctl cat <服务名>` 和 `systemctl show <服务名> -p Environment` 核对
   `ExecStart`、`WorkingDirectory`、环境文件与数据库、素材等运行路径。部署脚本和部署后的
   人工复核都复用这组已解析事实，不在不同阶段重新猜路径。
2. 将远端代码结构、启动命令和 release 标识与本地 `package.json`、目标提交和制品哈希比对。
3. 确认反向代理端口、数据库实际路径、备份位置和回滚 release，不把同机其他服务当成本项目。
4. 部署前排除环境文件、凭据、`.DS_Store` 等敏感或无关内容。macOS 自带 `bsdtar` 不支持
   GNU tar 的 `--transform`，需要目录改名时使用 `-s` 或先构建明确的制品目录；跨平台上传
   文档或批量数据时使用 `COPYFILE_DISABLE=1 tar --no-xattrs`，并在解包后断言不存在 `._*`
   AppleDouble 伴生文件，避免它们被误当业务输入。
5. 切换后回读服务状态、运行版本、探针、正式库和备份完整性。复核命令失败时先区分“验证器使用
   了错误路径或参数”与“运行系统故障”，用独立的服务、探针和配置证据复查后再下结论。
6. 验证结果只说明对应环境，不扩大为正式生产或客户验收。
7. SSH 身份必须作为“本地私钥 + 远端用户 + 主机”三元组验证；云控制台里的密钥标签不等于
   本地私钥文件名。仓库记录不完整时，先搜索同项目已成功的部署记录和本地会话历史，再用
   `BatchMode=yes` 对候选三元组做一次只读连接，不要重复向作者索要已经提供过的地址或密钥。
8. 非交互 SSH 不保证继承交互 shell 的 `PATH`，固定 Node/npm 等运行时应显式加入 PATH 后再做
   制品断言。workspace 中 `package.json#bin` 的相对路径以所在包目录为基准，不能从仓库根直接
   拼接。zsh 的 `path` 是与 `PATH` 绑定的特殊数组，部署脚本循环变量使用 `endpoint` 等普通名称，
   避免只读验证意外清空后续命令搜索路径。
