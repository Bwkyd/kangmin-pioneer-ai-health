# 报价范围先于产品补全

功能分组和开发计划必须先区分三类内容：

1. 客户材料或报价明确写明的交付功能；
2. 为实现已承诺功能不可缺少的技术能力；
3. 根据代码缺口、体验连贯性或产品判断提出的候选改进。

第三类即使合理、重要或能形成更完整闭环，也不能自动升级为报价内范围、P0 任务或开发授权。分别写入报价的两个功能，也不能未经确认就推导出两者之间的联动、历史、入口或统计能力。

正式建立开发计划前必须完成以下核验：

- 直接读取当前权威原件，并定位到工作表、栏目或条目；
- 对照客户决策和最新范围变更，确认是否覆盖该功能及其联动方式；
- 把原文范围、必要技术实现和候选增项分别列出；
- 只有原文明确或作者明确批准的内容才能标记为“已确认，待开发”。

如果缺少读取原件的工具、权限或运行时，只能记录“待原件核验”，不得依赖历史摘要继续扩大解释，也不得生成正式实施计划。代码已经具备某项数据、页面存在某个缺口、产品体验需要补全，都只能证明技术现状，不能证明合同或报价承诺。

发现范围依据错误时，应立即停止开发并把过程材料移入临时区。尚未提交、未进入正式仓库的候选材料应从正式文档、状态板细节和编号索引中完全移除，不消耗正式编号；已经提交或对外采用的计划才保留撤回记录和已使用编号。两种情况都必须防止后续会话把旧材料当成授权。
